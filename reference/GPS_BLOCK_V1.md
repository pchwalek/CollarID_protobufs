# GPS block v1: packed GPS fixes for LoRaWAN uplinks

Wire contract between the collar firmware (encoder), the server decoder, and
this repository (the `Deployment.gps_block` field, the reference codec in
`reference/gps_block.py`, and the test vectors in
`test_vectors/gps_block_v1.json`). The words MUST and MUST NOT are normative.
Where this text and the reference codec disagree, that is a bug to be fixed in
one of them; the vectors are generated by the codec.

## 1. Why

A `GPSData_2` entry costs 28 to 31 B on air: protobuf int32 at 1e-7 degree
(a negative coordinate is a 10-byte varint), a 5-byte timestamp, and per-fix
metadata. At 5 fixes per packet, a collar taking a fix every 5 minutes and
uplinking hourly lost 7 of every 12 fixes. Measured on about 4,300 field
fixes: 12 fixes cost 354 B as `gps_data` (does not fit an uplink) and about
55 B as a block; 24 fixes have a median of about 100 B and a real worst case of
about 160 B.

## 2. Wire placement

- `message.proto`, `Deployment`: `optional bytes gps_block = 10;`
- nanopb options, in the master `message.options` of this repository:
  `Deployment.gps_data max_count:24` and `Deployment.gps_block max_size:180`.
  The collar firmware has no options file: it vendors the generated
  `message.pb.h`, and static_asserts and firmware host-test guards pin both
  sizes (24 fixes, 180 B), so a header generated with other options fails
  the firmware build and its host tests.
  180 = UPLINK_BUDGET_FIT_LORAWAN (227) - 44 B that the uplink budget never
  strips (header <= 33, deployment wrapper 3, battery 3, errorFlags 5) - 3 B
  field tag and length. A firmware host test pins this arithmetic against
  `uplink_budget.h`.
- LoRaWAN deployment uplinks carry their fixes in `gps_block`. LoRa
  point-to-point frames carry ONLY `gps_data`, at most 5 entries: the NEWEST 5
  of the accumulator in arrival order (last entry = newest), because the
  handheld finder (nanopb `max_count:5`) and the website handheld page decode
  `gps_data`.
- Firmware MUST NOT emit both fields in one frame (host-test enforced). A
  decoder that meets both logs a warning, drops each `gps_data` entry that has
  the same timestamp as a block entry and lies within 50 (1e-7 degree) of it on
  both axes, and returns the union sorted ascending by timestamp (stable;
  legacy entries before block entries on ties), so the last entry is the
  newest.
- `header_epoch`: the encoder MUST use the value already written to this
  frame's `MessagePacket.header.epoch` (never a second clock read), and every
  re-pack during budget fitting uses that same value. The decoder MUST use the
  raw on-air `header.epoch` of the same frame (0 is a valid value), never a
  sanitised, None-mapped, AUTO-SYNC-corrected or anchor-corrected epoch. Block
  fix times are absolute GNSS times; clock corrections never apply to them.
  Replays on fPort 12 are verbatim, so the relation holds for them too.

### 2a. Extensions (how v1 grows without a v2)

1. The core block changes only with a version bump. Version 0 is reserved and
   invalid. A decoder MUST ignore (and log) a block whose version it does not
   implement and still decode the rest of the frame. Rollout order for any new
   version: server first, then firmware.
2. Additive per-fix data goes in sibling `optional bytes` fields of
   `Deployment` (next free field numbers). Each is a column whose entry k
   belongs to wire-order fix k of the core block, and each starts with its own
   3-bit column version. Decoders ignore sibling columns they do not know and
   still decode the core. The firmware re-encodes siblings whenever it
   re-packs.
3. Per-block scalars (counters, totals) go in ordinary optional protobuf
   fields, never inside the block.

## 3. Primitives

- Bit order: most significant bit first. Fields are written back to back with
  no alignment. The last byte is padded with zero bits; pad bits MUST be 0.
- `W(u)`: bit length of an unsigned integer u; W(0) = 0. A field of width 0
  occupies no bits and reads as 0.
- Zigzag on signed 64-bit x, written so C has no undefined behaviour:
  `zz(x) = x >= 0 ? 2*(uint64)x : 2*(uint64)(-(x + 1)) + 1`;
  `unzz(u) = (u & 1) ? -(int64)(u >> 1) - 1 : (int64)(u >> 1)`.
  zz(0) = 0, zz(-1) = 1, zz(1) = 2, zz(-2) = 3.
- Quantization of a coordinate v (1e-7 degree, int32) to 1e-5 degree:
  `q(v) = floor((v + 50) / 100)`, mathematical floor, computed in int64.
  C integer division truncates toward zero, so implement floor division
  explicitly (q(-151) = -2, not -1). Reconstruction: `v' = 100 * q`, an
  integer in 1e-7 degree. Error |v - v'| <= 50: at most 0.56 m per axis,
  0.79 m horizontal, about 0.39 m on average. About 0.4 % of consecutive field
  fixes become identical positions.
- All arithmetic on times, sums and differences is done in 64-bit integers.
  Both operands are widened BEFORE subtracting (`(int64)a - (int64)b`).

## 4. Input fixes

Each fix: `lat_e7` (int32), `lon_e7` (int32), `t` (uint32 Unix seconds, GNSS
time of the fix), `h_acc_dm` (uint32; 0 or absent = unknown), `ttff_s`
(uint32; absent is read as 0).

The collar's accumulator holds up to 24 fixes (`Deployment.gps_data
max_count:24`, the reason for that option); the wire limit is 32.

The encoder:

- EXCLUDES a fix when any of these holds (explicit comparisons, never abs()):

  ```
  lat_e7 < -900000000 || lat_e7 > 900000000 ||
  lon_e7 < -1800000000 || lon_e7 > 1800000000 ||
  (q(lat_e7) == 0 && q(lon_e7) == 0) || t < 1767225600
  ```

  1767225600 is CLOCK_GATE_EPOCH (2026-01-01), the gate the server and the
  firmware already share. The null island test is on the QUANTIZED position
  (section 3), so a fix within 50 (1e-7 degree) of (0, 0) on both axes
  (lat_e7 and lon_e7 both in [-50, 49], since q rounds half up) is excluded
  rather than silently skipped by the decoder: (30, -40) and (-50, 49) are
  excluded; (50, -50) quantizes to (1, 0) and (-51, -99) to (-1, -1), and
  both are kept (a truncating q would wrongly exclude the latter). The C
  API exports this predicate as `gps_block_fix_excluded` (Python:
  `is_excluded`) so the caller can remove excluded fixes. An excluded fix
  can never be sent: the caller MUST remove it from its accumulator. N is
  the number of fixes remaining after exclusion.
- requires 1 <= N <= 32; otherwise it emits nothing.
- orders the fixes NEWEST FIRST as the exact reverse of a STABLE ASCENDING sort
  by t (C: insertion sort of an index array ascending, then read it backwards;
  never qsort, never copy fix structs). On ties the wire therefore holds the
  reverse of the input order, and the decoder's oldest-first output restores
  the input order.
- The reference encoder validates types and ranges and raises on anything
  outside int32 / uint32.

## 5. Accuracy (6 bits per fix)

`code = 0` if h_acc_dm is 0 or absent (unknown); otherwise
`code = h_acc_dm > 620 ? 63 : ceil(h_acc_dm / 10)` (whole metres rounded up,
computed so it cannot overflow).

Decoder: 0 -> `h_acc_m` None (unknown); 1..62 -> `h_acc_m = code` (an upper
bound within 1 m); 63 -> `h_acc_m = 63` (an integer, like every decoded
value), meaning "63 m or worse" (the collar accepts at most 100 m, on the boot
fix only). Unknown and "worse than 62 m" are never merged.

| h_acc_dm | 0 | 1 | 10 | 11 | 620 | 621 | 2^32-1 |
|---|---|---|---|---|---|---|---|
| code | 0 | 1 | 1 | 2 | 62 | 63 | 63 |
| h_acc_m | None | 1 | 1 | 2 | 62 | 63 | 63 |

## 6. Layout

Fix 0 is the newest (wire order, section 4).

```
field        bits          value
version      3             1
n_minus_1    5             N - 1                          (N = 1..32)
lat0         25            zz(q(lat_e7[0]))               (|q| <= 9,000,000 -> zz < 2^25)
lon0         26            zz(q(lon_e7[0]))               (|q| <= 18,000,000 -> zz < 2^26)
age_w        6             W(zz(age))                     (<= 33)
age          age_w         zz(age), age = (int64)header_epoch - (int64)t[0]
-- time to fix
if N == 1:
  ttff0      10            min(1023, ttff_s[0])
if N >= 2:
  ttff_kmax  W(N-1)        wire index of the fix with the largest RAW uint32 ttff_s (compare
                           before saturating; lowest index on ties)
  ttff_max   10            min(1023, ttff_s[kmax])
  ttff_rest  10            min(1023, (2*S + M) div (2*M)), S = uint64 sum of ttff_s over the
                           other M = N-1 fixes (round-half-up mean)
acc[k]       6 x N         accuracy code of fix k (section 5), k = 0..N-1
-- only when N >= 2:
lat_w        5             W(max_k zz(dlat_k))            (<= 26)
lon_w        5             W(max_k zz(dlon_k))            (<= 27)
dtmin_w      6             W(dt_min)                      (<= 32)
dt_min       dtmin_w       min_k dt_k
dt_w         6             W(max_k (dt_k - dt_min))       (<= 32)
then for k = 1 .. N-1, in order:
  dlat_k     lat_w         zz(q(lat_e7[k]) - q(lat_e7[k-1]))
  dlon_k     lon_w         zz(q(lon_e7[k]) - q(lon_e7[k-1]))
  ddt_k      dt_w          dt_k - dt_min, dt_k = (int64)t[k-1] - (int64)t[k]  (>= 0 by the sort)
-- zero padding to a byte boundary
```

ttff_kmax and ttff_max are chosen on the raw uint32 `ttff_s` values; S sums
the raw values; saturation to 1023 is applied last. Comparing saturated values
gives a different kmax whenever two or more values saturate: wire-order ttff
[1500, 3000, 10] has kmax = 1 on the raw values, where saturated values
(1023, 1023, 10) would tie and give 0.

Length (informative; the normative check is walking the layout):

```
bits  = 65 + age_w + 6N + (N == 1 ? 10
                                   : W(N-1) + 42 + dtmin_w + (N-1)(lat_w + lon_w + dt_w))
bytes = ceil(bits / 8)
```

On the wire the field costs 2 more bytes (tag and length) when the block is
<= 127 B, and 3 more for 128 to 180 B.

Block size is NOT monotone in N: removing a fix can make the block larger (age
and the shared widths change; for example, dropping one fix from a regular
series opens a time gap that every remaining row pays for in dt_w). After any
change to the fix set the caller recomputes; it never assumes that removing a
fix frees bytes.

## 7. Decoder rules

The decoder runs inside its own error boundary: a bad block never drops the
rest of the frame.

- A zero-length `gps_block` carries no fixes and is not an error.
- Version 0 or any version other than 1: ignore the block (log).
- Corrupt (ignore the whole block and log it) when:
  - any field would be read past the end;
  - a width field exceeds its maximum (age_w > 33, lat_w > 26, lon_w > 27,
    dtmin_w > 32, dt_w > 32);
  - ttff_kmax >= N;
  - the byte length is not exactly ceil(bits / 8) for the layout walked;
  - any pad bit is 1;
  - any reconstructed q_lat is outside [-9,000,000, 9,000,000] or q_lon
    outside [-18,000,000, 18,000,000];
  - any reconstructed t is outside [1767225600, 2^32 - 1].
- Times: t[0] = header_epoch - age; t[k] = t[k-1] - dt_k, dt_k = dt_min +
  ddt_k.
- Coordinates: lat_e7 = 100 * q_lat and lon_e7 = 100 * q_lon as integers;
  degrees = lat_e7 / 1e7 (one division, the same expression as the legacy
  gps_data path). Never multiply by 1e-7.
- A reconstructed fix at q = (0, 0) makes the block corrupt: the whole block
  is ignored, not just that fix (the encoder never emits one, section 4).
- The decoder does not enforce the 180 B nanopb cap: any length that walks
  the layout exactly is accepted. The cap binds the encoder only.
- Per fix output: lat, lon, timestamp t, h_acc_m (section 5), gps_fix_time_s
  (N = 1: ttff0; N >= 2: ttff_max for fix kmax, ttff_rest for every other
  fix), altitude_mm None, hdop None.
- Entries are returned OLDEST FIRST (reverse wire order), so the server's
  "last entry = current position" convention holds.

### Lossy by design

- Positions are kept to 1e-5 degree (at most 0.56 m per axis).
- h_acc is kept as a whole-metre upper bound (on average 0.45 m high); h_acc
  above 62 m reads 63.
- Time to fix keeps each block's maximum exactly and replaces the others by
  their mean, so a block's average and maximum survive (values above 1023 s
  saturate at 1023).
- Altitude and HDOP are not carried (the collar does not send them today
  either).

## 8. Encoder API

```
/* pure; the exact number of bits the layout needs for these fixes (after
   exclusion, sorted as section 4), or 0 when N is outside 1..32 */
size_t gps_block_bits(const fix *f, size_t n, uint32_t header_epoch);
/* writes ceil(bits/8) bytes to out and returns that count; returns 0 and
   writes NOTHING when N (after exclusion) is outside 1..32 or the result
   exceeds cap. MUST refuse, never truncate. */
size_t gps_block_encode(const fix *f, size_t n, uint32_t header_epoch,
                        uint8_t *out, size_t cap);
```

The firmware passes cap = sizeof(Deployment.gps_block.bytes) (180). Which
fixes to carry when the block does not fit is the caller's policy (the
firmware drops the newest arrival and re-encodes; the dropped fixes stay in
the accumulator for the next uplink).

The C API also exports the exclusion predicate of section 4,
`gps_block_fix_excluded`, so the caller can remove excluded fixes from its
accumulator.

The Python reference (`reference/gps_block.py`) has the same functions,
`is_excluded(fix)`, `gps_block_bits(fixes, header_epoch)` and
`gps_block_encode(fixes, header_epoch, cap)` (returns `b""` where C returns
0), and `decode(block, header_epoch)`, which returns `("ok", fixes)` oldest
first, `("empty", [])`, or `("ignored", reason)`.

## 9. Test vectors

`test_vectors/gps_block_v1.json`, generated by `reference/make_vectors.py`
from the reference codec and checked in (`make_vectors.py --check` and the
unit tests fail when it is stale). The vectors are SYNTHETIC: this repository
is public, so no vector holds a real position, time or device id. Every track
is at a fictional location with times in 2027 or later (apart from cases that
sit on the constants 1767225600 and 2^32-1); the realistic batches only
reproduce the statistics of field data.

- `vectors`: `{name, note, header_epoch, cap, fixes: [{lat_e7, lon_e7, t,
  h_acc_dm, ttff_s}], bits, hex, decoded: [{lat_e7, lon_e7, t, h_acc_m,
  gps_fix_time_s}], hex_uncapped?}`. `gps_block_encode(fixes, header_epoch,
  cap)` must give `hex` (null when the encoder must emit nothing),
  `gps_block_bits` must give `bits` (0 when N is outside 1..32), and decoding
  `hex` must give `decoded`, oldest first.
  - `cap`: the cap passed to the encoder; 180 unless the vector tests the cap.
  - `decoded` is `[]` when `hex` is null.
  - `hex_uncapped`: present only on over-cap vectors (the cap alone refused
    the block); the block without a cap, which the decoder must still decode.
  - A fix may omit `h_acc_dm` (unknown) or `ttff_s` (read as 0).
- `decoder_only`: `{name, why, header_epoch, hex, expect}`, where `expect` is
  `"ignored"`, `"empty"`, or the decoded list.
- `note` and `why` are free text for humans; tests ignore them.

All comparisons are on integers (`h_acc_m` and `gps_fix_time_s` are integers
or null; 63 is the integer 63).

Coverage, at least: single fix; N = 2 identical positions (lat_w = lon_w =
0); 3 identical fixes where the length lands just past a byte boundary;
stationary jitter; a moving track; southern + western hemisphere; lat and lon
exactly on the half step, positive and negative; equal timestamps (decoded
order == input order); unsorted input; age 0, age -1, large negative age;
header_epoch 0 with a real fix time; antimeridian crossing; lat +-90 and lon
+-180; INT32_MIN coordinates (excluded); (0, 0) input (excluded); fixes
within 50 of (0, 0) that quantize to it (excluded) next to one that does not;
t below the clock gate (excluded); 33 fixes of which one is excluded (N = 32);
every accuracy code boundary (0, 1, 10, 11, 620, 621, 2^32-1 dm); ttff
saturation including 2^32-1 and ties for the max; a ttff case where kmax
differs between raw and saturated comparison (wire-order ttff [1500, 3000,
10] -> kmax 1) and one where the saturated values tie but the raw maximum is
a later index; ttff_s absent (read as 0), N = 1 and N >= 2; realistic N = 12
and N = 24 hourly batches (synthetic); a 24-fix vehicle track near the cap;
an N = 32 moving track over the 180 B cap (hex null for cap 180).
Decoder-only: zero-length block; 1-byte block; truncated header; non-zero
padding; extra trailing byte; version 0; version 2; lat0 out of range; a
delta that walks past the pole; ttff_kmax >= N; a width above its maximum; t
below the gate after reconstruction; a fix reconstructed at q = (0, 0), as
the newest fix and after a delta (ignored); the over-cap block (decodes).

The firmware host test and the server tests both load these vectors (the
firmware through a generated header that records the JSON's sha256).

## 10. Server consumers

- Deploy order: protobufs main, then server, then firmware. The api
  Dockerfile canary asserts `gps_block` is in `Deployment`'s fields, so a
  stale proto fails the build instead of silently dropping fixes.
- A replay (fPort 12) that fills no open gap is a duplicate, and its rows are
  dropped, only when the server already stores the same frame: same device,
  same `packet_index` and the same payload bytes (a replay is the verbatim
  on-air frame), stored within 60 days (counted back from the frame's build
  time, its header epoch, or from its arrival when that epoch is below the
  clock gate or later than arrival). Storing it again would duplicate every
  fix of its block. A replay of a reused index whose content differs is a
  different frame and is kept.
- Conformance: for frames whose GPS came from a block, the GPS deliverable is
  the scheduled count (the per-packet cap existed because a packet carried at
  most 5 fixes). Per-hour packet capacity is counted from the hour a packet
  was received, never from the times of the GPS fixes it carries, for block
  and legacy `gps_data` rows alike (both are stored at their fix times, which
  can lie in hours before the uplink that carried them).
- Current-position queries order by `received_at` and break ties by
  insertion order, so among fixes with the same time the one stored last
  (the decoder's last entry, section 7) is the current position.
- `telemetry_points.gps_codec` ('block_v1' for rows decoded from a block,
  NULL otherwise) records which rows carry block precision.

## 11. Non-goals for v1

A DR-aware soft target (trimming the block to land under a data-rate
threshold); 2D/3D fix type (can come later as a sibling column, section 2a);
fix-success and GPS on-time counters (ordinary fields, later); altitude.
